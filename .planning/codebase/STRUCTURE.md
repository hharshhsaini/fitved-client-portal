## Directory Purposes

**`src/pages/`:**
- Purpose: one file per route, the composition root for a screen.
- Contains: data-fetching hooks, page-level layout, feature logic; imports shared components from `src/components/`.
- Key files: `src/pages/Landing.tsx` (marketing homepage), `src/pages/admin/Trainers.tsx` (largest admin page, trainer CRUD + off-time/session accounting), `src/pages/TrainerDashboard.tsx`.

**`src/pages/admin/`:**
- Purpose: every route under `/admin/*`.
- Contains: `Dashboard.tsx`, `Customers.tsx`, `CustomerDetail.tsx`, `Plans.tsx`, `Trainers.tsx`, `Societies.tsx`, `Marketing.tsx`, `Referrals.tsx`.
- Key files: `CustomerDetail.tsx` composes the tab components from `src/components/admin/customer-tabs/`.

**`src/components/ui/`:**
- Purpose: shadcn/ui-generated Radix wrapper primitives — the design-system building blocks.
- Contains: `button.tsx`, `dialog.tsx`, `table.tsx`, `sidebar.tsx`, `select.tsx`, `form.tsx`, etc. — one component family per file, following the shadcn convention (not hand-rolled from scratch).
- Generated: effectively yes (shadcn CLI pattern) — treat as low-churn; prefer composing them over editing internals.

**`src/components/admin/`, `src/components/dashboard/`, `src/components/trainer/`, `src/components/plan/`:**
- Purpose: feature-specific components grouped by the role/page area that owns them, mirroring the `src/pages/` role grouping.
- Contains: dialogs (`AddCustomerDialog.tsx`, `TrainerReviewDialog.tsx`), tab panels (`customer-tabs/*.tsx`), dashboard widgets (`ClassCalendar.tsx`, `MarketingFeed.tsx`, `SocietyBatches.tsx`, `TrainerPauses.tsx`, `TrainerClientPauseModal.tsx`), the trainer profile form (`TrainerProfileForm.tsx`), and the plan-explore dialog (`ExplorePlansDialog.tsx`).

**`src/lib/`:**
- Purpose: pure, framework-agnostic domain logic and small utilities reused across pages.
- Contains: date/plan math, phone normalization, referral-earnings computation, the shared specializations constant, and the `homeForRole()` routing helper.
- Key files: `src/lib/routes.ts` (role → home route), `src/lib/specializations.ts` (single source of truth for the trainer specializations list), `src/lib/sessionPlan.ts` + `src/lib/trainerSessions.ts` (plan/session accounting math).

**`src/integrations/`:**
- Purpose: external-service client singletons, isolated so the rest of the app imports one thing (`supabase`, `firebaseAuth`).
- Contains: `supabase/client.ts` + `supabase/types.ts` (generated — "Do not edit directly" per its own header comment), `firebase/client.ts`.

**`src/stores/`:**
- Purpose: React Context "stores" for cross-page domain state (not Redux/Zustand — just Context + exported helper functions).
- Contains: `pauseStore.tsx` — `PauseProvider` plus the exported `recalculatePlanDates()` function called from many mutation `onSuccess` handlers across client and admin pages.

**`public/`:**
- Purpose: static assets served as-is by Vite/Vercel, including hand-authored SEO pages and a foreign embedded app.
- Contains: per-keyword landing pages (`personal-training.html`, `yoga-classes-bangalore.html`, etc.), `booking-modal.js` (widget script) + gitignored generated `booking-config.js`, and `societies/` (built static export of a separate Next.js repo — see ARCHITECTURE.md "Static-site embedding" pattern).
- Generated: `societies/` and `booking-config.js` are build outputs, not hand-edited.

**`supabase/migrations/`:**
- Purpose: ordered SQL schema history for the Supabase Postgres project.
- Contains: 31 files as of this analysis, from early schema through `20260728160000_poll_area_requests.sql` (society-poll area requests). Filenames are timestamp-prefixed; two use the `YYYYMMDDHHMMSS_<uuid>.sql` Supabase-generated naming, later ones use `YYYYMMDDHHMMSS_<slug>.sql` for readability.
- **Caveat:** the live Supabase project's actual schema can be ahead of or diverge from what's applied here — migrations are run manually via the Supabase SQL editor, not an automated CI migration step. Always confirm columns exist on the live REST API before depending on a migration file.

**`supabase/functions/`:**
- Purpose: Supabase Edge Functions (`create-customer`, `create-trainer`, `reset-customer-dob`).
- Contains: three function directories; per project memory these were largely superseded by direct frontend `supabase.from(...)` writes and may not be currently deployed — verify deployment status before adding logic here.

**`scripts/`:**
- Purpose: Node/bash utility scripts run manually or via `npm run` hooks, not part of the app runtime bundle.
- Contains: `generate-booking-config.js` (runs automatically pre-dev/pre-build), `build-societies.sh` (manual — rebuilds the embedded societies sub-site), `migrate-trainers-to-firebase.mjs` and `upload-society-images.mjs`/`seed-poll-db.mjs` (one-off data-migration scripts).

- `.env` / `.env.local` (gitignored): `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_FIREBASE_*` — never read/quote contents; presence noted only.

**Core Logic:**
- `src/contexts/AuthContext.tsx`: all auth flows (client/admin/trainer).
- `src/stores/pauseStore.tsx`: plan-date recalculation engine.
- `src/lib/sessionPlan.ts`, `src/lib/trainerSessions.ts`: session/plan accounting math.
- `src/lib/referrals.ts`: referral-earnings derivation.

**Testing:**
- `src/test/setup.ts`: Vitest + Testing Library setup (loaded via Vitest config).
- `src/test/example.test.ts`: sole existing test file — see TESTING.md for details (quality-focus doc, not covered in this arch pass).

## Naming Conventions

**Files:**
- React components/pages: PascalCase matching the exported component (`TrainerProfileForm.tsx`, `AppSidebar.tsx`, `Dashboard.tsx`).
- Non-component modules (hooks, lib helpers, integration clients): camelCase (`useProfile.ts`, `phoneAuth.ts`, `client.ts`).
- shadcn `ui/` primitives: lowercase-kebab matching the Radix component (`dropdown-menu.tsx`, `alert-dialog.tsx`, `input-otp.tsx`) — follow this convention exactly when adding new shadcn components (use the shadcn CLI convention, not PascalCase, inside `ui/`).
- Migrations: `YYYYMMDDHHMMSS_<descriptive_slug>.sql`, always ascending chronological, in `supabase/migrations/`.

**Directories:**
- Feature-area component folders are named after the role/domain they belong to (`admin/`, `dashboard/`, `trainer/`, `plan/`), mirroring the `src/pages/` structure — when adding a new trainer-only component, put it in `src/components/trainer/`, not a flat `src/components/` root.
- `src/pages/admin/*` mirrors `/admin/*` routes 1:1; non-admin pages sit flat in `src/pages/`.

## Where to Add New Code

**New client-facing feature/page:**
- Primary code: new file in `src/pages/` (flat, PascalCase, matching the intended route name), registered in `src/App.tsx`'s `<Routes>` under the `ProtectedRoute allow={["client","admin"]}` block if client-scoped.
- Supporting components: `src/components/dashboard/` if it's a dashboard widget, otherwise a new subfolder mirroring the feature.
- Tests: `src/test/` (currently minimal convention — see TESTING.md).

**New admin feature/page:**
- Primary code: `src/pages/admin/<Name>.tsx`; register the route in `src/App.tsx` under `ProtectedRoute allow={["admin"]}`, and add a sidebar entry in `src/components/AppSidebar.tsx`'s admin `items` array.
- Supporting components/dialogs: `src/components/admin/` (or `src/components/admin/customer-tabs/` specifically for new Customer Detail tabs).

**New trainer feature/page:**
- Primary code: `src/pages/Trainer<Name>.tsx` (flat, `Trainer`-prefixed, matching existing `TrainerDashboard.tsx`/`TrainerReferrals.tsx`/`TrainerProfile.tsx` convention); register under `ProtectedRoute allow={["trainer","admin"]}` in `src/App.tsx`, add to `trainerItems` in `AppSidebar.tsx`.
- Supporting components: `src/components/trainer/`.

**New shared domain logic (calculations, formatting, derivations):**
- Add a new module to `src/lib/` (pure functions, no React/Supabase imports where possible) rather than inlining logic in a page component — follow the existing pattern of `sessionPlan.ts`/`trainerSessions.ts`/`referrals.ts`.

**New Supabase table/column:**
- Add a new timestamped SQL file to `supabase/migrations/` following the existing naming pattern; do NOT assume it's live until manually run against the Supabase project. Until confirmed live, feature-detect (see ARCHITECTURE.md "Feature-flagged schema access" pattern) rather than assuming the column exists.
- Regenerate `src/integrations/supabase/types.ts` once the migration is confirmed live, and remove any temporary `as any` casts added for that table/column.

**New shadcn/ui primitive:**
- Add to `src/components/ui/` using the shadcn CLI naming/style convention (lowercase-kebab filename, Radix-wrapped export) — do not hand-roll a divergent style for a primitive that shadcn already provides.

**Utilities:**
- Shared, non-domain helpers (classnames, generic formatting) go in `src/lib/utils.ts`; domain-specific helpers get their own file in `src/lib/`.

## Special Directories

**`public/societies/`:**
- Purpose: built static export of an entirely separate Next.js repository ("Society Poles", maintained outside this repo).
- Generated: Yes — via `scripts/build-societies.sh`, which builds the external Next.js app and copies its `out/` into this directory (with an image-path flattening step).
- Committed: Yes (checked into this repo despite being generated), because Vercel serves it directly as static files — do not hand-edit; changes must originate in the external Next.js project and be re-baked via the build script.

**`public/booking-config.js`:**
- Purpose: runtime config (`window.FVConfig = { url, key }`) for the standalone `booking-modal.js` widget embedded in static marketing HTML pages.
- Generated: Yes — via `scripts/generate-booking-config.js`, run automatically before `npm run dev`/`npm run build`.
- Committed: No — explicitly gitignored (`/public/booking-config.js` in `.gitignore`).

**`supabase/functions/`:**
- Purpose: Supabase Edge Functions.
- Generated: No (hand-written), but per project memory largely unused/superseded — verify current deployment relevance before extending.
- Committed: Yes.

**`docs/specs/`:**
- Purpose: freeform prose specs for specific features (admin dashboard, plan options + WhatsApp, trainer routing/capabilities) — supplementary design notes, not enforced contracts.
- Generated: No.
- Committed: Yes.
